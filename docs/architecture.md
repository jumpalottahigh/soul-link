# Soul Link Architecture

Implementation reference for the single-page, mobile-first partner app. Repository-wide development rules and commands live in [AGENTS.md](../AGENTS.md); deployment/setup instructions live in [README.md](../README.md).

## Screen Flow and Auth

There is no router. `App` renders a splash while loading, `AuthScreen` without a session, `ResetPasswordScreen` during recovery, and `PairingScreen` without a paired profile. Otherwise it renders `MainApp`, with Mood, Invites, Trip Planner, and Bingo tabs plus settings/custom-mood dialogs.

`main.tsx` wraps the tree in `StrictMode` and `AuthProvider`. `AuthContext.tsx` owns session, profile, partner profile, and recovery state. The context object/type and `useAuth()` are in `useAuth.ts` for Fast Refresh; a separate `authContext.ts` filename would clash on case-insensitive filesystems. The hook throws outside the provider.

`useAuth()` exposes session/user/profiles/loading, sign-up/sign-in/sign-out, `refreshProfile`, password reset/update actions, `recoveryMode`, and `exitRecoveryMode`. Auth actions return an error string or null rather than throwing. Sign-up passes `display_name` in user metadata; a server-side trigger, not client code, creates the profile row.

`PASSWORD_RECOVERY` sets recovery mode. Reset emails redirect to `window.location.origin`, and recovery takes precedence over pairing until `exitRecoveryMode()`. Profile loading fetches the user first and then their partner when `partner_id` is set; pairing calls `refreshProfile()` afterward. MainApp's profile/user non-null assertions rely on these rendering gates.

## Core Data Model

Supabase is the entire backend. Base profile/invite schema and pairing logic live in the deployed project; the repository contains the separate Trip Planner and Bingo SQL scripts.

- `profiles`: auth user `id`, `display_name`, `mood_emoji`, `mood_label`, `drawing`, `gender`, `partner_id`, `invite_code`, `recent_moods`, and `updated_at`.
- `drawing` is a JSON array of strokes; `recent_moods` is a JSON array of emoji/label pairs. Gender is `male`, `female`, or `other`.
- `invites`: `id`, `sender_id`, `receiver_id`, `activity`, free-text `time`, `status` (`pending`, `accepted`, or `declined`), and `created_at`.
- `pair_with_code(code)` returns success/partner/error information. Pairing authorization is enforced by the RPC and RLS, not a direct profile update.
- Pair codes are six characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, generated by `generatePairCode()` and stored in `profiles.invite_code`.

Realtime must be enabled for profiles/invites. The trip and Bingo scripts configure publication entries for their own tables and can be applied independently and repeatedly in the Supabase SQL editor.

## MainApp State and Realtime

MainApp initializes local mood, drawing, gender, display name, and recent moods once from the paired profiles. Profile refreshes do not automatically reinitialize that state; subsequent partner updates arrive through realtime. Writes update local state first and log persistence failures. Drawing writes are debounced by 500 ms; mood/gender/name writes are immediate.

The `partner-profile` channel listens for profile updates filtered to the partner ID and updates their mood, drawing, and gender. `invites-sync` listens to invite changes under RLS: inserts prepend, updates replace, and deletes are not handled. Invites are fetched on mount, and `mapDbInviteToInvite` maps sender IDs to `me` or `partner`. Channels are removed during effect cleanup to prevent StrictMode duplicates.

Recent moods contain at most five distinct emoji/label pairs, most recent first. `MoodView.getDisplayMoods` pads missing entries with defaults, alongside a Custom button. `CustomMoodModal` uses `Intl.Segmenter` for grapheme-aware emoji input. Gender drives the three-way Her/His/Partner labels across mood, drawing, and pairing copy. Unpairing has no UI.

## Drawing

The stored shape is `Drawing = Stroke[]`, with each stroke containing `points: Point[]`. Coordinates are normalized from 0 to 1; the canvas has a fixed 2.2:1 aspect ratio. The entire drawing is overwritten in `profiles.drawing`, so payload size grows with stroke count.

`DrawingCanvas` edits the user's drawing. Touch listeners are native and non-passive so iOS Safari allows `preventDefault`; mouse input uses React handlers. Refs keep native listeners synchronized with current drawing/callback values. A stroke commits only with at least two points, and the trash action clears all strokes.

`DrawingPreview` shows the partner's drawing at 0.4 alpha and renders nothing when empty. Both read the accent CSS variable for theme-aware stroke color.

## Theming

Themes are `default` (Rose), `dark` (Night), and `cute` (Cute). The stored theme uses `us-app-theme`, applies through `data-theme` on the HTML element, and initially falls back to `prefers-color-scheme`.

Theme CSS variables in `global.css` are registered with Tailwind's `@theme`, enabling utilities such as `bg-page`, `bg-card`, `text-text`, `text-accent`, and `border-border-accent`. Theme additions affect the CSS theme blocks/registration, `Theme` and `THEMES` in `types.ts`, and App's `themeCardColors`/`themePageColors` maps. App also sets the browser theme-color meta tag: card color when logged in, page color otherwise.

Trip event colors are the separate, non-theme-specific `--event-color-1..5` variables, with fixed dark event text.

## Trip Planner

Trips belong to a couple and use client-generated UUIDs. `trips` stores `id`, `owner_id`, `name`, `start_date`, and `end_date`; `trip_events` stores `id`, `trip_id`, `title`, `date`, `start_minute`, and `end_minute`. RLS's `can_access_trip(owner_id)` allows the owner or their partner to read/update/delete; inserts require the signed-in owner. Deleting a trip cascades to events.

`useTripPlanner` holds trips and `eventsByTrip`. Events load lazily for the active trip; an absent cache key means not yet loaded. The selected ID is stored as `us-app-active-trip` and falls back to the first trip. Optimistic writes return booleans; failures clear the event cache, reload server state, and show an error banner. The `trip-planner` channel handles trip/event changes, including deletion by ID.

`TripPills` switches/creates trips. The selected trip's shared `ActionsMenu` provides rename, date adjustment, and two-step deletion. `TripDialog` handles create, rename, and date adjustment. `PlannerHeader` displays the saved date range and grid hours; it is not the date editor.

`DayPlanner` uses a 07:00-23:00 grid with same-day events and side-by-side overlap layout. Events outside the trip range remain stored but hidden. Tapping empty grid space opens `EventEditor`; there is no separate Add event button. Interactjs handles drag/resize. Shared geometry constants (`DAY_WIDTH`, `HOUR_HEIGHT`, `TIME_WIDTH`) in `lib/trip/schedule.ts` keep rendering and interaction math aligned.

## Bingo

Each named board has 25 shared text cells and separate completion marks for each partner. `bingo_boards` stores the owner, name, and creation time; `bingo_cells` stores board ID, position 0-24, and text; `bingo_marks` stores cell ID, user ID, and completion. Board/cell deletions cascade, and each cell/user mark pair is unique.

The SQL access helper authorizes the board owner or their partner. Secured RPCs handle board creation, cell text, and marks; board rename/delete use the database helpers. Creation inserts a board and exactly 25 cells transactionally. Mark writes use the authenticated user's ID, not a caller-selected user. Clearing cell text resets both partners' marks atomically, and blank cells cannot be marked.

`useBingo` holds boards, cells, and marks. The selected board ID uses `us-app-active-bingo`, falling back to the first board. Mutations update optimistically, prevent overlapping writes, restore a snapshot on failure, and reload server data. The `bingo` realtime channel invalidates the three tables with a debounced reload. Loading, retry, busy, and persistent error states are exposed to the view.

`BingoView` opens existing boards in Play and newly created boards in Edit. Play toggles only the current user's marks; Edit changes shared text. Empty cells are blank/disabled in Play and display a centered plus in Edit. Partner marks use initials and distinct visual shapes/colors. Cell text is centered, with actual marks positioned separately near the bottom.

The selected board's `ActionsMenu` provides rename and delete. `BingoDialog` handles create, rename, cell text, and delete confirmation; failed saves keep the dialog open with an inline error.

`countBingos` counts each user's five rows, five columns, and two diagonals independently. Empty/whitespace cells and false marks do not count. There is no free center; a full board has 12 lines. Native Node tests cover line counts, independence, blank cells, and initials.

## Shared Menus and Dialogs

`ActionsMenu` is a native auto popover with an ellipsis trigger, menu-item semantics, arrow/Home/End navigation, Escape focus restoration, and Tab dismissal. Horizontal positioning is clamped to the closest `main` column with margins, rather than only to the viewport. Stable item IDs retain focus when confirmation labels change; `keepOpen` supports Trip's two-step deletion.

Text-entry dialogs focus their input or textarea after `showModal()`. Trip rename/date adjustment/event dialogs and Bingo rename/item dialogs open near the top with safe-area spacing and bounded scrolling for mobile keyboards. Create/delete dialogs keep their existing centered positioning where applicable. Tailwind preflight resets native dialog margins, so positioning requires explicit margin utilities.

## Mobile Layout and Tooling

The app is a centered `max-w-md` column with safe-area header spacing and a pinned bottom navigation; content spacing clears the navigation. `index.html` uses `viewport-fit=cover`, disables zoom, and sets Apple web-app meta tags. There is no service worker or manifest.

Only theme and the selected trip/Bingo IDs are local preferences. Contents and progress remain in Supabase. TypeScript uses type-only imports, erasable syntax, and unused-declaration checks; ESLint rejects `any`. The compiler/API compatibility aliases and required commands are documented in the canonical agent guide rather than duplicated here.
